# Security Architecture & Vulnerability Audit Report
**Project:** RetailPulse Decision Intelligence (DI) Platform  
**Target Architecture:** Local Enterprise Deployment (Python 3.13, Microsoft SQL Server 2025 Developer, Streamlit)  
**Security Posture:** Zero-Trust Data Quarantine, Parameterized Persistence, Integrated Authentication  

---

## 1. Authentication & System Trust Boundaries

### 1.1 Local Integrated Windows Authentication (`-E`)
- **Zero Hardcoded Secrets:** The application relies exclusively on Windows Integrated Authentication (`Trusted_Connection=yes;TrustServerCertificate=yes`) to interact with Microsoft SQL Server on `localhost`.
- **No Plaintext Passwords:** No database passwords, access tokens, or shared secrets are stored in code, configuration files, environment variables, or Git history.
- **Kerberos / NTLM Local Token Exchange:** Database access tokens are dynamically negotiated by the Windows Local Security Authority (LSA) using the caller's active OS user context.
- **Auditing in `.gitignore`:** Strict exclusion rules ensure that `.env`, `.env.*`, `.streamlit/secrets.toml`, and credential files cannot be committed to version control.

## 2. Defense-in-Depth Against SQL Injection (SQLi)

### 2.1 100% Parameterized Query Enforcement
Every analytical query, data loading routine, and decision write-back across the system uses parameterized bind variables:
- **T-SQL via `pyodbc`:** Prepared statements with `?` parameter markers and `cursor.executemany()` or `cursor.execute(sql, (param1, param2))`.
- **SQLAlchemy 2.x Integration:** Queries in `src/ui/data_access.py` and analytical modules bind parameters via `sqlalchemy.text()` with dictionary binding (`:store_id`, `:product_id`, `:limit`).
- **Static Code Audit:** Automated repository scans verified zero user-controlled string interpolation (`f"..."`, `format()`, `%s`) in SQL commands.

### 2.2 Relational Foreign Key Integrity
- All transactional and snapshot facts enforce database-level foreign key constraints against `dim_date`, `dim_store`, `dim_product`, and `dim_supplier`.
- Inserting orphaned product keys or out-of-range calendar dates results in immediate database-level transaction termination (`FK_fact_po_exp_date`, `FK_repl_date`).

## 3. Data Quarantine & Schema Validation Firewall

### 3.1 Pre-Ingestion Pydantic V2 Isolation
The ingestion pipeline ([`src/etl/ingest.py`](file:///d:/Documents/Documents/RetailPlus_AI/src/etl/ingest.py)) acts as a strict firewall:
- Inbound CSV payloads are parsed into strongly typed Pydantic models with custom field validators (`Field(gt=0)`, `Field(ge=0)`, `iso8601_date_validator`).
- Malformed records (negative sales prices, missing foreign keys, future dates) are intercepted before touching dimensional or fact tables.

### 3.2 Dead-Letter Quarantine (`dbo.quarantine_records`)
- Intercepted corrupt records are routed to an isolated quarantine table:
  ```sql
  CREATE TABLE dbo.quarantine_records (
      quarantine_id        VARCHAR(50) PRIMARY KEY,
      source_feed          VARCHAR(50) NOT NULL,
      raw_payload_json     NVARCHAR(MAX) NOT NULL,
      violation_category   VARCHAR(50) NOT NULL,
      violation_details    NVARCHAR(1000) NOT NULL,
      rejected_at          DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME(),
      batch_id             VARCHAR(50) NOT NULL
  );
  ```
- **Auditability:** Every quarantined row captures full execution lineage (`batch_id`, UTC timestamp, and raw JSON payload) ensuring complete root-cause forensic analysis without pipeline disruption.

## 4. Operational Decision Integrity & Authorization

### 4.1 Idempotent Write-Back
Decision recommendations generated by the HiGHS MILP optimizer are saved idempotently into `dbo.fact_replenishment_recommendation`:
- Prior unapproved proposals for the target run date are cleared atomically within the transaction before inserting a fresh batch.
- Duplicate primary key violations (`recommendation_id`) are eliminated.

### 4.2 State Machine Transition Rules
Order recommendations strictly adhere to a codified lifecycle:
$$\text{PROPOSED} \longrightarrow \{\text{APPROVED}, \; \text{MODIFIED}, \; \text{REJECTED}\}$$
- The state transition engine validates status against an enumerated whitelist (`{'PROPOSED', 'APPROVED', 'MODIFIED', 'REJECTED'}`).
- Modifying order quantities automatically recalculates total procurement spend (`estimated_cost = units * unit_cost`) at the database level to prevent financial ledger discrepancy.
